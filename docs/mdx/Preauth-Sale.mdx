# Process a payment authorization

<Tags tags={frontmatter.tags} />

Authorizations can be initiated as a sale or pre-authorization, which is defined in the request by sending the `captureFlag` in `transactionDetails`.

- *false:* A pre-authorization transaction, where the customer's funds will be reserved and a [capture](/product/CommerceHub/docs/Payment-Operations/Manage-Payments/Capture.mdx) will be required to withdraw the funds.
- *true:* A sale or subsequent capture transaction where the customer will be charged the total amount, and funds withdrawn.

- [**Authorization only:**](/product/CommerceHub/docs/Payment-Methods/Payment-Methods.mdx) A transaction where the merchant [verifies](/product/CommerceHub/docs/Value-Added-Services/Account-Services/Verification.mdx) a customer's account, also known as a $0 authorization.
- [**Pre-authorization:**](/product/CommerceHub/docs/Payment-Methods/Payment-Methods.mdx) A transaction where the customer is authorized to have funds withdrawn from their account on a future date.
- [**Estimated:**](/product/CommerceHub/docs/Payment-Operations/Accept-Payments/Estimated-Auth.mdx) A pre-authorization transaction where the final amount is not known, normally followed by an incremental authorization.
- [**Sale:**](/product/CommerceHub/docs/Payment-Methods/Payment-Methods.mdx) A transaction where the customer is authorized to have funds withdrawn from their account at the end of the day.
- [**Capture:**](/product/CommerceHub/docs/Payment-Operations/Manage-Payments/Capture.mdx) A transaction where the merchant requests to have the pending funds from a pre-authorization withdrawn from the customer account at the end of the day.
- [**Incremental:**](/product/CommerceHub/docs/Payment-Operations/Accept-Payments/Incremental-Auth.mdx) A transaction where the merchant requests to increase the original pre-authorization.

**Argentina:**

- Does **not** support $0 authorizations, the [Account Verification API](/product/CommerceHub/docs/Value-Added-Services/Account-Services/Verification.mdx) should be used to verify the customer's account.
- Does **not** support captures, if a pre-authorization is submitted to verify funds, it must be [cancelled](/product/CommerceHub/docs/Payment-Operations/Manage-Payments/Cancel.mdx) the same day, and a sale processed instead to capture the payment.

**Mexico:**

- Does **not** support partial authorization.
- Does **not** currently support incremental authorization and estimated authorization.

## Parameters

This section outlines the key parameters relevant to the API request. These parameters are essential for understanding how to interact with the API effectively. For a complete list of request and response variables, refer to the full request schemas available in the [API Explorer](/product/CommerceHub/api/post/payments/v1/charges).

### Request variables

<Alert type="warning" variant="inline" className="w-full">
  <AlertIcon />
  <AlertTitle>⚠️ Warning</AlertTitle>
  <AlertDescription>

If the merchant account is enabled for a [tokenization service](/product/CommerceHub/docs/Payment-Methods/Tokenization/Tokenization.mdx), `paymentTokens` will be returned in the response. If a multi-use token is required, the [stored credentials details](/product/CommerceHub/docs/Payment-Methods/Tokenization/Stored-Credentials.mdx) must be submitted in the request. To override this behavior, set `createToken` to *false* in `transactionDetails`.

  </AlertDescription>
</Alert>

<Alert type="warning" variant="inline" className="w-full">
  <AlertIcon />
  <AlertTitle>ℹ️ Info</AlertTitle>
  <AlertDescription>

The merchant can skip BIN lookup by sending `binVerification`: `SKIP_FOR_TOKENIZATION` in the request as part of [transaction details](docs/Resources/Master-Data/Transaction-Details.md). This does not override the behavior for an authorization which will still decline for an invalid BIN.

  </AlertDescription>
</Alert>
